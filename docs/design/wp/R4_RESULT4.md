## 0. 한 줄 결론

**R4 게이트 미통과, 운영 승인 비권고(critical 1).** 3차 결함 N8·N9·N10·N11·N12·m-b 와 D22-5 는 실데이터에서 **해결**됐다 — 같은 스냅샷 재판정
(a)·(a2)·(a3) 세 번 모두 `tools/call` **0**(프록시 = 잡 = `judgment_log`), 같은 날 daily 뒤 판정기 추출 납부 조건 6건 '확인됨' 유지 · `missing_provenance`
0, 46·47 법정동이 1회차 안에서 결정, bootstrap 사실 이벤트 0(`first_load` 한 줄). 그러나 ① 같은 날 `collect.daily`(b)가 이미 받은 경쟁률 원문을
다시 정규화하면서 **경쟁률 행 70개를 중복으로 새로 만들어**(단지 11개, 바뀐 원문 없음) 발행 리비전 5에 '확인됨' Fact 140개가 change_event 없이
생겼다(**critical N13 — 발행 결과가 조용히 바뀜**). ② 같은 재정규화가 판정기 compare 채택 표식을 지워 47개 필드의 '판정기 compare 채택'
근거가 사라졌고, (b) 뒤 재판정이 새 compare **4회**를 불렀다(**N14 — (b) 뒤 `tools/call` 0 위반**). ③ 첫 시도(00:01)는 청약홈 API 데이터셋이
비어 있던(`totalCount 0`) 시간대에 돌아 단지 24개짜리 스냅샷이 아무 경고 없이 발행됐다(**N15**) — DB 를 지우고 데이터셋이 돌아온 01:01 에 다시

## 14. 하지 않은 것 / 가정

- 코드·계약·픽스처는 고치지 않았다. DB 는 R4 DB 의 public 테이블만 지웠고(두 번) 그 밖은 SELECT 만 했다.

- 2회차 (b)는 "다음 날"이 아니라 1회차 약 6분 뒤 같은 기준일에 돌렸다. 그 사이 실제 공고 1건(2026940221)이 새로 올라왔다 — (b)의 변화·재판정은 그 단지에 한정됨을 확인했다.

- 프론트는 띄우지 않았다(API 응답으로 G1·G2·G3·G7 표본만 확인).
- N13·N14·N15 의 원인 설명은 코드 읽기와 DB 상태·원문으로 확인했고 수정 테스트는 쓰지 않았다. N14 의 '같은 rank 상충이면 값이 빈다'는 resolver 규칙에서 추론한 위험이며 이번 데이터에서 재현되지 않았다. 1회차 시간 단축 원인은 추정이다.

- 원문·보고서·로그·API 응답은 scratchpad `r4d/`, 데이터는 R4 DB 에 남겨 두었다. r4 env·사본·토큰·접속 주소 파일은 지웠고 API 프로세스는 멈췄다.

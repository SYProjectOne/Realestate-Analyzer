# 청약·부동산 사이트 UI 벤치마크 → 우리 화면 개선 — 메타 프롬프트 (REA MCP)

## 0. 사용법 (사람이 읽는 부분 — 복사하지 않는다)

1. 관찰용 Chrome을 디버그 포트로 띄운다. 9222는 Aside가 쓰고 있으니 9333을 쓴다. 평소 쓰는 Chrome 프로필과 분리된다.

   ```powershell
   Start-Process "C:\Program Files\Google\Chrome\Application\chrome.exe" -ArgumentList '--remote-debugging-port=9333','--user-data-dir=C:\tmp\rea-chrome','--no-first-run','--window-size=1440,900'
   ```

   모바일 화면도 볼 거라면 두 번째 창을 `--remote-debugging-port=9334`, `--user-data-dir=C:\tmp\rea-chrome-m`, `--window-size=420,900`으로 하나 더 띄운다.
2. 그 Chrome에서 벤치마크할 페이지들을 탭으로 연다. 로그인이 필요한 페이지는 열지 않는다. 같은 `--user-data-dir`로 다시 실행하면 이미 떠 있는 창에 탭이 추가된다. 아래는 §2-1 Tier 1 홈을 한 번에 여는 명령이다. 각 사이트에서 목록·상세 페이지까지는 사람이 직접 클릭해 연다.

   ```powershell
   $t1 = 'https://www.applyhome.co.kr','https://apply.lh.or.kr','https://www.i-sh.co.kr','https://apply.gh.or.kr','https://hogangnono.com','https://asil.kr','https://kbland.kr','https://fin.land.naver.com','https://www.zigbang.com','https://aptgin.com','https://www.richgo.ai','https://rt.molit.go.kr'
   Start-Process "C:\Program Files\Google\Chrome\Application\chrome.exe" -ArgumentList (@('--user-data-dir=C:\tmp\rea-chrome') + $t1)
   ```

   탭이 많으면 REA가 느려진다. Tier 단위로 열고, 관찰이 끝난 탭은 닫는다.
3. 우리 앱을 띄운다: `cd frontend && npm run dev:msw`. Chrome 탭에서 `http://localhost:5173`도 연다.
4. 아래 §1~§9를 통째로 복사한다. `[ ]` 변수 6개를 채워 Claude Code·Codex·Cursor 중 하나에 붙인다. 셋 다 REA MCP와 `reverse-engineer-anything` 스킬이 전역으로 설치돼 있다.
5. 에이전트는 Phase 4에서 멈추고 개선안 승인을 기다린다. 승인한 항목만 구현된다.

## 1. 역할과 목표 — 여기부터 복사

당신은 부동산 서비스 UX를 개선하는 프로덕트 디자이너이자 React 프론트엔드 엔지니어다. 청약·부동산 정보를 오래 다뤄 온 국내 서비스들이 화면을 어떻게 구성하는지 REA MCP로 관찰한다. 거기서 얻은 근거로 우리 앱(`subscription-analyzer`)의 화면과 보고서를 `[대상 사용자]`가 한눈에 읽을 수 있게 고친다.

지금 우리 화면의 문제는 "정보는 다 있는데 읽기 어렵다"는 것이다. 숫자·배지·표·출처가 같은 무게로 한꺼번에 나와 무엇을 먼저 봐야 할지 모른다. 보고서도 표가 길고 결론이 뒤에 있다. 목표는 **데이터와 규칙은 그대로 두고, 정보 계층·배치·문구·시각적 무게를 바꿔 이해 속도를 높이는 것**이다.

다른 사이트의 디자인을 베끼는 작업이 아니다. 구조와 패턴(무엇을 먼저 보여주고, 어떻게 묶고, 어디서 펼치는지)만 배운다.

## 3. 지켜야 할 규칙

### 3-1 관찰 규칙 (외부 사이트)

1. 공개 페이지만 관찰한다. 로그인·본인인증·청약 신청 화면은 열지도, 조작하지도 않는다.
2. REA는 수동 관찰만 한다. 폼 제출·클릭 자동화·크롤링 반복을 하지 않는다. 한 페이지를 한 번 관찰하고 끝낸다.
3. 관찰은 UI 구조에 필요한 것만 켠다. `inspect_web_page`에는 `include_accessibility_text`만 켠다. `include_script_sources`·`include_storage_keys`·`include_console_text`·`include_json_body_shapes`·`include_websocket_shapes`·`analyze_web_bundle`은 쓰지 않는다. 남의 API·코드는 우리 작업 범위가 아니다.
4. 결과는 패턴으로만 남긴다. 다른 사이트의 로고·이미지·아이콘·문구·색 팔레트·CSS·코드를 우리 저장소에 옮기지 않는다. 노트에는 "무엇을 어떤 순서로 어떻게 묶었는가"를 우리 말로 적는다.
5. 스크린샷 PNG는 저장소 밖 `C:\tmp\ui-bench\shots\`에만 둔다. 커밋하지 않는다. 저장소에는 텍스트 노트와 `evidence_id`만 남긴다.
6. 사이트가 막으면(403·봇 차단·빈 화면) 우회하지 않는다. "관찰 불가(사유)"로 기록하고 다음 사이트로 간다.

### 3-2 우리 저장소 규칙 (`AGENTS.md` 요약 — 원문이 이긴다)

1. 쓰는 곳은 `frontend/`(`package.json` 제외)와 그 테스트, 노트 폴더 `docs/design/ui-benchmark/`뿐이다. 보고서 템플릿(`backend/app/reports`, WP8)·API·계약을 바꿔야 하면 직접 고치지 않고 Phase 6 보고의 "요청"에 적는다.
2. 새 라이브러리를 추가하지 않는다. 지금 스택만 쓴다: React 18, TypeScript, Vite, Tailwind, TanStack Query/Table/Virtual, ECharts, React Router. 필요하면 "제안"에 적는다.
3. 화면 문자열은 `frontend/src/i18n/ko.json` 한 곳에만 둔다. 숫자 포맷(억·만·%)은 `FactCell`만 한다.
4. 판단을 UI에서 만들지 않는다. "추천"·"좋음/나쁨"·확률·순위를 프론트에서 새로 계산하거나 요약 문구로 지어내지 않는다. 보여주는 것은 API가 준 판정기 결과·점수·라벨뿐이다. 순서·강조·접기만 바꾼다.
5. 숨기지 않는다. 출처 URL·확인일·라벨(추정·비공식·재가공·확인 불가·사람 확인)은 단순화 과정에서 사라지면 안 된다. 접어도 되지만 한 번의 클릭으로 닿아야 하고, 빈 라벨은 테스트 실패다.
6. 화면 공통 규칙(DECISIONS D7)은 유지한다.
   - 빈 값은 "확인 불가(사유)"로 표시한다.
   - 날짜는 기준일 대비 D±를 함께 쓴다.
   - 라이트·다크 테마를 모두 지원한다.
   - 모바일(≤768px)은 G1·G2·G3를 읽기 전용으로 보여준다.
   - 판정 화면 하단에 "투자 권유 아님 · 상대 비교"를 고정한다.
   - 라벨은 색이 아닌 텍스트 배지로 표시한다.
   - 차트 데이터는 표로 열어볼 수 있어야 한다.
   - 발행 스냅샷 값과 현재 값을 한 행에 섞지 않는다(D10-1).
7. 지역명을 코드에 하드코딩하지 않는다. 지역명은 픽스처·테스트에만 나온다.
8. 테스트를 먼저 쓴다. 커밋 전에 `npm run lint`, `npm run typecheck`, `npm test`를 통과시킨다. 화면 구조를 바꿨으면 `npm run e2e:pages`도 돌린다.
9. 커밋 접두는 `[WP6]`으로 하고, `[작업 브랜치]`에만 커밋한다. main에 커밋하지 않는다.

## 4. 작업 절차

### Phase 0 — 도구 확인 (5분)

- `list_browser_targets(endpoint=[CDP 엔드포인트])`로 열린 탭을 확인한다. 실패하면 멈추고 §0의 Chrome 실행 명령을 사용자에게 다시 안내한다.
- REA 스크린샷은 **보이는 뷰포트만** 찍고 스크롤하지 않는다. 아래쪽 내용이 필요하면 사용자에게 "○○ 페이지를 △△까지 스크롤해 달라"고 요청한 뒤 다시 찍는다.
- 스크린샷 결과의 `artifact.data_base64`는 PNG로 디코드해 `C:\tmp\ui-bench\shots\<사이트>-<페이지>-<뷰포트>.png`로 저장하고, 이미지를 직접 열어 본다. 접근성 트리만으로 시각적 무게를 판단하지 않는다.

### Phase 1 — 우리 앱 진단 (먼저 한다)

벤치마크 전에 우리 화면부터 같은 도구로 본다. 비교 기준이 같아야 한다.

1. `[우리 앱 URL]`에서 `[개선 대상]`의 각 화면을 탭으로 연다. 각 화면마다 `inspect_web_page(allowed_origins=[우리 앱 origin], include_accessibility_text=true)`와 `capture_web_screenshot`을 실행한다. 데스크톱·모바일 둘 다 한다.
2. 화면마다 아래 항목을 적는다.
   - **첫 화면 3초 테스트**: 스크롤 없이 보이는 영역에서 `[대상 사용자]`가 처음 읽게 되는 것 3개, 실제로 먼저 읽어야 하는 것 3개, 그 차이
   - 한 뷰포트 안의 숫자 개수, 배지 개수, 같은 무게의 요소 개수
   - 설명 없이 나오는 전문 용어 목록
   - 출처·라벨이 본문을 가리는 곳, 반대로 찾기 어려운 곳
   - 상태 화면(로딩·빈 값·오류·확인 불가)의 모습
3. 보고서(G8)는 최신 산출물 하나를 읽고, 첫 페이지에 결론이 있는지, 표 하나의 열 수와 행 수, 용어 설명 유무를 적는다.
4. 결과는 `docs/design/ui-benchmark/00-baseline.md`에 쓴다.

### Phase 2 — 벤치마크 관찰

관찰량이 많다(약 27곳 × 3페이지 이상). 맥락이 넘치지 않게 나눠서 한다.

- 서브에이전트를 쓸 수 있으면(Claude Code `Agent`) Tier별 또는 사이트별로 맡긴다. 서브에이전트는 노트 파일만 쓰고, 패턴 한 줄 요약과 `evidence_id`만 돌려준다. 관찰 원본(JSON·접근성 트리)을 메인 대화에 붙이지 않는다.
- 서브에이전트가 없으면(Codex·Cursor) 사이트 하나를 끝낼 때마다 노트를 파일에 쓰고, 다음 사이트로 넘어가기 전에 그 원본은 다시 읽지 않는다.
- 순서는 Tier 1 → Tier 2 → Tier 3이다. Tier 1이 끝나면 중간 패턴 목록을 한 번 정리하고, 이후 사이트에서는 "이미 본 패턴의 반복인가, 새 패턴인가"를 표시한다.

`[벤치마크 사이트]`의 각 페이지마다 `inspect_web_page`(접근성 텍스트만)와 `capture_web_screenshot`을 실행한다. 데스크톱과, 가능하면 모바일도 찍는다. 페이지마다 아래 양식으로 `docs/design/ui-benchmark/10-<사이트>.md`에 적는다.

```markdown
## <사이트> — <페이지 종류> (<URL>, 관찰일 YYYY-MM-DD, evidence_id …)
- 첫 화면에서 가장 먼저 보이는 것 3개(크기·위치 순):
- 정보 계층: 1단(결론/요약) → 2단(핵심 수치) → 3단(상세/원문) 각각 무엇인가
- 묶음 단위: 카드 / 표 / 탭 / 아코디언 / 지도 — 언제 무엇을 쓰는가
- 숫자 표기: 단위, 반올림, 범위 표현, 비교 기준(전월·주변 시세 등)
- 상태·라벨 표현: 접수중/마감/예정, 경고, 출처 표기 위치
- 필터·정렬: 기본값, 노출 개수, 접는 방식
- 용어 처리: 툴팁 / 괄호 설명 / 용어집 링크 / 아예 쉬운 말로 바꿈
- 모바일에서 달라지는 것:
- 우리에게 쓸 만한 패턴(우리 말로 한 줄씩):
- 우리에게 맞지 않는 것과 이유(광고·로그인 유도·근거 없는 추천 문구 등):
```

### Phase 3 — 패턴 종합과 갭 분석

1. 사이트 노트를 가로질러 패턴을 뽑고, 각 패턴에 근거가 된 `evidence_id`와 사이트 수를 단다. 등급은 셋으로 나눈다.
   - **강한 패턴**: 4곳 이상, 국내·해외 모두에서 나옴
   - **검증된 패턴**: 2곳 이상
   - **참고**: 1곳에서만 나옴
   
   국내 사용자 습관(네이버·호갱노노·KB에서 익숙한 순서)과 해외 패턴이 충돌하면 국내 습관을 우선하고, 충돌 사실을 결정 사항으로 남긴다.
2. 패턴 범주는 다음과 같다.
   - 요약 우선 배치
   - 상태 배지
   - 핵심 수치 카드
   - 표 밀도와 열 선택
   - 상세 페이지 탭 구조
   - 용어 설명
   - 출처 표기
   - 비교 화면
   - 빈 상태
   - 모바일 축약
   - 보고서 첫 장 구성
3. 우리 화면(Phase 1)과 대조해 갭 표를 만든다.

   | # | 화면 | 지금 문제(Phase 1 근거) | 검증된 패턴(근거) | 바꿀 것 | 영향 파일 | 효과(상·중·하) | 품(S·M·L) | 지켜야 할 규칙 |
   |---|---|---|---|---|---|---|---|---|

4. 효과는 상이고 품은 S·M인 것부터 정렬한다. 결과는 `docs/design/ui-benchmark/20-gap.md`에 쓴다.

### Phase 4 — 개선안 (여기서 멈추고 승인을 받는다)

갭 표 상위 항목마다 아래를 낸다.

- 전·후 ASCII 와이어프레임(데스크톱 1개, 모바일 1개)
- 바뀌는 정보 계층: 1단·2단·3단에 무엇이 오는지
- 새로 생기거나 바뀌는 `ko.json` 키와 문구 초안. 문구는 `[대상 사용자]`가 아는 말로 쓰되, 판정을 새로 만들지 않는다
- 숨기지 않는다는 증거: 출처·라벨·확인일이 어디로 옮겨 가고 몇 번 클릭에 닿는지
- 보고서 개선은 WP8 소유라 **요청서 초안**으로 낸다(첫 장 요약 구성, 표 분할, 용어 부록 등)

결과는 `docs/design/ui-benchmark/30-proposal.md`에 쓴다. 판단이 갈리는 지점(예: 표를 기본 접기 vs 펼치기)은 "결정 사항"으로 모아 사용자에게 묻는다. **승인 전에는 코드를 고치지 않는다.**

### Phase 5 — 구현 (승인된 항목만)

1. 항목마다 테스트를 먼저 쓴다. 정보 계층 순서, 라벨·출처 접근 가능 여부, 빈 값 "확인 불가(사유)", 모바일 읽기 전용, 고정 문구를 검증한다.
2. 기존 공용 컴포넌트를 먼저 재사용한다: `FactCell`, `LabelBadge`, `ProvenancePanel`, `EmptyState`, `DataTableToggle`, `PageShell`. 새 컴포넌트는 `frontend/src/components/`에 두고 `components.contract.test.tsx` 규칙을 따른다.
3. 색·간격은 Tailwind 기존 토큰만 쓴다. 색만으로 의미를 전하지 않는다.
4. 구현 후 Phase 1과 같은 탭·뷰포트로 다시 찍고 `compare_web_screenshots`로 전·후를 비교한다. 첫 화면 3초 테스트를 다시 채점한다.
5. `npm run lint`, `npm run typecheck`, `npm test`, `npm run e2e:pages`가 모두 통과해야 커밋한다.

### Phase 6 — 완료 보고 (`AGENTS.md` 양식)

```markdown
## 완료 보고 — WP6 UI 벤치마크 (계약 {최신}, 브랜치 [작업 브랜치])
산출물: {파일 목록}
관찰: 사이트 {n}곳 · 페이지 {n}개 · 관찰 불가 {목록과 사유}
테스트: `{명령}` → {통과/전체}
전·후: 화면별 첫 화면 3초 테스트 점수, 한 뷰포트 숫자·배지 개수 변화
완료 기준: [x] … [ ] …(사유)
하지 않은 것 / 가정한 것: …
제안(새 라이브러리·설계 개선): …
요청(WP8 보고서·WP5 API·계약): 대상 · 변경 내용 · 이유 · 없으면 "없음"
```

## 5. 완료 조건

- Tier 1 12곳 전부, Tier 2 8곳 전부, Tier 3 3곳 이상에 관찰 노트 또는 "관찰 불가(사유)"가 있다. 관찰에 성공한 사이트는 15곳 이상이다.
- 모든 패턴에 `evidence_id`와 사이트 수가 달려 있고, 구현에 쓴 패턴은 "검증된 패턴" 이상이다.
- 보고서 레퍼런스 3종의 첫 장 구성 비교가 WP8 요청서에 들어 있다.
- 갭 표의 모든 행이 Phase 1의 실제 관찰을 근거로 한다.
- 구현된 화면에서 출처·확인일·라벨이 하나도 사라지지 않았고, 이를 테스트가 증명한다.
- 프론트에서 새로 만든 판정·추천 문구가 없다.
- 다른 사이트의 자산·문구·코드가 저장소에 없고, 스크린샷 PNG가 커밋되지 않았다.
- lint·typecheck·test·e2e:pages가 통과한다.
- 전·후 스크린샷 비교와 3초 테스트 재채점이 보고에 있다.

## 6. 하지 말 것

- "더 예쁘게"를 목표로 삼기. 목표는 "더 빨리 이해"다. 근거 없는 리디자인·테마 교체는 하지 않는다.
- 다른 사이트의 추천 문구("지금 사세요", "핫한 단지")를 흉내 내기. 우리 앱은 판정기 결과만 보여준다.
- 정보를 줄인다며 데이터를 삭제하기. 줄이는 방법은 순서·접기·요약 위치뿐이다.
- 한 번에 전 화면 갈아엎기. 효과 상·품 S부터 화면 단위로 끊어서 한다.

# 지역 청약 리스트업·분석 프로그램 — 설계 메타 프롬프트

2026-10-08 · @라홈

## 0. 사용법

이 문서는 "특정 지역의 청약 리스트업·분석 프로그램"을 설계하라고 AI(Claude·Cursor 등)에 지시하는 메타 프롬프트다. §1~§2를 통째로 복사해 `[ ]` 자리 6개를 채워 붙이면 프로덕션급 웹 GUI 분석 도구의 설계 문서(아키텍처·데이터 모델·모듈·판정 규칙·화면 8종·차트 10종·운영 요건·완료 조건)가 나온다. 인천 3개 신도시·김포 보고서(JEV 호출 132회)에서 실제로 통한 절차를 그대로 규칙화했고, 그 프로젝트에서 부족했던 16가지(§4 회고)를 §2-6~2-9의 화면·차트·운영·판정 품질 규칙으로 바꿔 넣었다.

| 단계 | 할 일 | 나오는 것 |
|---|---|---|
| 1. 변수 채우기 | §1-2 표의 `[지역]` `[기준일]` `[내 조건]` `[기술 스택]` `[판정기]` `[출력 형식]` 6개를 채운다. 모르는 것은 "미지정"으로 두면 기본값이 적용된다 | 완성된 프롬프트 |
| 2. 설계 요청 | §1~§2 전문을 붙이고 "§2-10의 16개 산출물을 순서대로 작성하라"고 말한다 | 설계 문서 |
| 3. 설계 검토 | §2-11 완료 조건 22개로 한 줄씩 따져 묻고, 비는 것은 수정 지시 | 확정 설계 |
| 4. 구현 요청 | 확정 설계를 붙이고 "모듈 M1(수집)부터 하나씩 구현"을 요청(구현은 설계와 별도 대화) | 코드·보고서 템플릿 |
| 5. 회귀 테스트 | §3-1의 인천·김포 파라미터와 결과로 같은 숫자가 나오는지 확인 | 검증된 v1 |

세 가지만 지키면 된다. 한 번에 한 지역만 돌린다. 설계와 구현은 다른 대화에서 한다(한 대화에 섮으면 설계가 코드에 끈려간다). JEV MCP가 없는 환경이면 `[판정기]`에 "LLM 자체 판정 + 사람 검수"라고 적어 임계값 규칙을 대체한다.

## 1. 메타 프롬프트 본문 (1/2) — 여기부터 복사

### 1-1 역할과 목표

당신은 부동산 청약 리서치 시스템을 설계하는 소프트웨어 아키텍트이자 부동산 데이터 분석가다. 목표는 ******의 민간분양 아파트를 전수 리스트업하고, "현재 구매가 대비 상승 여력"을 외부 판정기로 판정해 ****웹 GUI(대시보드·차트·출처 드릴다운)로 보여주고 표 중심 보고서로 내보내는 프로덕션급 분석 도구**의 설계 문서를 작성하는 것이다. 프로그램은 지역을 바꿔 끼워도 같은 절차로 돌아야 하고, 모든 수치에 출처·확인일이 붙어야 하며, 판정은 프로그램이 직접 하지 않고 판정기에 맡긴다. 코드를 쓰지 말고 설계만 하라. 설계는 §2-10의 산출물 순서를 따르고, 판단이 갈리는 지점은 "결정 사항"으로 따로 모아 내게 묻는다.

### 1-3 범위 규칙 (프로그램이 자동으로 적용)

1. **대상** = `[지역]` 내 민간분양 아파트(주상복합의 아파트 부분 포함). (A) 기준일 현재 청약 접수 중 + 12개월 내 공고 예정, (B) 잔여물건(무순위·임의공급·선착순) 두 트랙으로 나눈다.
2. **제외** = LH·GH·iH·지방도시공사가 사업주체인 공공분양(사전청약 포함), 공공·민간임대, 오피스텔·도시형생활주택·생활형숙박시설, 범위 밖 소재(단지명으로 검색에 걸리는 타 지역 주의).
3. **경계 판단은 사업주체 명의로** 한다: 공공택지 내 민간분양(공기관 출자 SPC 포함)과 정비사업 일반분양은 포함, 공고 전이면 "확인 불가(공고 전)"로 기록만 한다. 판단은 `[판정기]`의 분류 기능에 맡기고 review는 미해결로 표기한다.
4. **판정 대상**은 포함 단지 중 기준일에 접수 가능하거나 공고 이력이 있어 미정인 단지로 한정한다. 분양가 미공개(공고 전)는 "보류 — 공고 후 재판정", 접수 가능 여부 자체가 확인 불가이면 "참고 후보(순위만)"로 두고 확률 사다리는 돌리지 않는다.
5. **접수 가능** 판정은 공식 출처(공고문·청약홈·공식 분양 홈페이지 팝업)만 근거로 "가능 / 미정 / 확인 불가 / 불가"로 나눈다. 보도자료·블로그만 있으면 "비공식"이고 "가능"이 될 수 없다.

## 2. 메타 프롬프트 본문 (2/2)

### 2-1 판정 파이프라인 (`[판정기]`가 판단하고, 프로그램은 입력을 만들고 결과를 기록한다)

| 단계 | 도구(JEV 기준) | 입력 | 출력 → 사용처 | 규칙 |
|---|---|---|---|---|
| P1 입력 검사 | jev_screen | 단지별 공고 발췌, 벤치마크·호재 텍스트 | pass/skip/block | skip(관련도 낮음)이면 목적(purpose)을 단계에 맞게 바꿔 다른 입력으로 재스크린; block은 사용 금지 |
| P2 수치 추출 | jev_extract | 공고문 txt + 필드 스키마(§1-5) | 필드값 + auto/review | review 필드는 공고문 원문값을 쓰고 "review" 표기, 같은 입력 재호출 금지 |
| P3 감사 | jev_audit | P2 레코드 + 원문 | pass/flagged(p_wrong) | flagged는 원문 대조 후 수정, 산술값(합계 등)은 "산술" 표기 |
| P4 분류 | jev_classify | (a) 포함/제외 — 사업주체 명의 기준 7클래스 (b) 호재 단계 5클래스 | 클래스 + 확률 + auto/review | review·manual_review = 미해결, 상승 근거로 사용 금지 |
| P5 출처 충돌 | jev_compare | 같은 사실의 두 출처 문장 + aspects | same_fact/contradicts/different_facts | contradicts면 1차 자료(공고문·청약홈) 채택·2차 병기; 둘 다 2차면 병기하고 판정에 미사용 |
| P6 상승 확률 사다리 | jev_noul | 단지 증거 카드(≤2,000자) + 지역 벤치마크 + 제도 컨텍스트, 명제 4개 | +5/+10/+20/보합하락 확률 + likely/uncertain/unlikely | 명제 템플릿 고정(§2-2), 판정 대상만 실행 |
| P7 상대 순위 | jev_rerank | 모든 후보 카드(지역 확장 시 전체를 한 번에) + 고정 query | relevance 순위 | 후보군이 바뀌면 전체 재실행하고 점수 변화를 표기 |
| P8 상황별 결정 | jev_decide | 후보 ≤6 + 증거 + 우선순위 + 요건 3개 | 선택 + 확률 분포 + 요건별 supported/contradicted/unknown + warnings | escaped면 멈추고 사용자에게 질문; warning은 그대로 보고; 증거와 상이한 요건 판정도 숨기지 않고 해석만 붙임 |
| P9 검증 | jev_verify | 섹션별 주장 ≤16건 + 근거 텍스트 | verified/contradicted/unsupported/review | contradicted → 수정 후 문장을 나눠 재검증(새 입력), unsupported → "확인 불가" 또는 삭제, review → 미해결 기록; 최종 contradicted 0이 완료 조건 |

임계값은 도구 기본값을 쓰고 보고서에 적는다(JEV: screen block 0.75/review 0.25, extract·classify·noul auto 0.85, audit wrong_at 0.7, verify auto 0.8). 호출은 일련번호로 로그하고 도구별 집계를 부록에 낸다. `[판정기]`가 JEV가 아니면 같은 9단계를 대체 도구로 매핑하고, 없는 단계는 "사람 검수"로 설계한다.

### 2-4 운영·갱신

- 재조사 트리거: 청약홈에 새 공고(본청약·무순위·임의공급), 공식 홈페이지 팝업 변경, 중도금 납부일 경과, 규제지역 지정·해제, 호재 단계 변경(예타·기본계획·착공), 월별 미분양 발표.
- 주간 점검: 청약홈 목록 두 개 조회 → 변경분만 재수집 → 영향받는 단지만 P2~P9 재실행 → 캘린더·체크리스트 갱신.
- 버전: 보고서는 기준일별로 보관하고 숫자 변화는 "이전 → 현재"로 표기. 같은 입력으로 판정기를 다시 부르지 않고, 입력이 바뀌었을 때만 재판정한다.

### 2-5 제약

1. 공개 분양 정보만 수집·전송한다. 개인정보·인증키·비공개 자료는 저장하지도, 판정기에 보내지도 않는다.
2. 판정기의 review/escalate/escaped/invalid_response는 미해결로 남기고, 같은 입력 재호출로 답을 바꾸려 하지 않는다.
3. 사이트 접속 제한·robots·속도 제한을 우회하지 않는다. 못 읽으면 "확인 불가"다.
4. 투자 권유·수익 보장 표현 금지. 판정은 상대 비교임을 매번 밝힌다.
5. 지역별 파라미터(생활권 정의, 전매 기간 규칙, 벤치마크 단지, 호재 목록)는 코드가 아니라 설정 파일에 둔다.

### 2-7 시각화 명세

한 숫자는 표 또는 차트 한 곳에만 둘 수 있고, 차트의 데이터는 표로 열어볼 수 있어야 한다. 색은 의미만 실는다(확정 = 강조 1색, 비공식·미확정 = 회색). 범위는 점(중앙)+위스커로 그리고 떠다니는 막대는 쓰지 않는다. 색만으로 의미를 전하지 않는다(라벨 병기).

| 차트 | 답하는 질문 | 형태 | 표시 규칙 | 화면 |
|---|---|---|---|---|
| 상승 확률 사다리 | 이 단지가 오를 확률은 | 가로 막대 4개(+5/+10/+20/보합·하락), 0~1 | 임계선 0.85(likely)·0.15(unlikely), 라벨 텍스트, 명제 시점(연도 반기) 부제 | G3, G4(overlay는 점) |
| 가격 갭 | 지금 가격이 시세 어디에 있나 | 점+위스커: 현재 구매가 범위 vs 비교 단지 실거래 범위 | 억 단위 축, "신축/대체(준공년)" 배지, 연식 보정값은 점선 점 | G3, G4 |

### 2-9 판정 품질 보강 규칙 (§4 회고에서 나온 것 — 반드시 설계에 반영)

1. **원자 주장 검증**: verify에 보내는 주장은 "1 사실 = 1 주장"으로 프로그램이 자동 분할한다. "3개는 unlikely이고 나머지는 uncertain" 같은 복합 문장 금지.
2. **요건 사전 계산**: decide 요건(접근 가능성·규제 제약·자금)은 프로그램이 수치로 먼저 평가해 증거에 "충족/미충족 + 근거 숫자"를 적어 보낸다(예: 전매 종료 2028-09 < 매도 가능 시작 2030-03 → 충족). 판정기 결과가 사전 계산과 다르면 둘 다 표시하고 "증거와 상이" 배지.
3. **동률 규칙**: decide confidence < 0.6이면 1순위 하나가 아니라 상위 2개를 "동률"로 제시한다.
4. **rerank 고정 앞커**: 후보군이 바뀌면(지역 추가) 과거 후보를 전부 포함해 1회 호출하고, 이전 점수와의 차이를 열로 보여준다. 종합 점수는 항상 같은 호출의 값만 쓴다.
5. **공통 시점 사다리**: "입주 후 1년" 외에 "기준일+3년"·"기준일+5년" 명제를 추가해 입주 시기가 다른 단지를 같은 시점에서 비교하고, 연율 환산 열을 둔다.
6. **가격 갭 연식 보정**: 2020년 이후 신축이 없는 생활권은 대체 단지의 준공 연도를 보정한 값(지역 설정의 연식 프리미엄 계수, "추정" 라벨)과 미보정값을 나란히 보여준다.
7. **점수 함수 명시**: 공급·유동성·벤치마크 점수는 사람이 등급을 매기지 않고 설계에서 식으로 확정한다(예: 유동성 = 10 − 2×전매 종료까지 연수 − 3×거주의무 유무 − 계약금%/5, 하한 0). 식은 화면 툴팁에 그대로 보인다.
8. **민감도 자동 계산**: 가중치 ±10%p 변화에 TOP 5 구성이 바뀜면 "순위 불안정" 배지.
9. **접수 상태 3경로**: 공식 팝업(자동) + headless 렌더링 스크린샷(자동) + 사람 확인 입력(전화·방문). 사람 확인은 날짜·입력자·내용을 남기고 "사람 확인" 라벨로 가능 판정에 쓸 수 있다. 비공식 보도는 참고 열에만.
10. **기본 필드 상충 자동 해결**: 세대수·면적·일정은 청약홈 상세 > 공고문 > 언론 순으로 채택하고 상충을 기록한다; 가격·전매 등 조건은 공고문 > 청약홈 > 언론. compare는 상충이 남은 것만 호출.
11. **자체 아카이브**: 청약홈 조회기간 제한에 대비해 매월 목록·공고문·경쟁률 스냅샷을 보관해 벤치마크 분양가를 언론이 아니라 공고에서 가져온다.
12. **호재 영향 매핑**: 역 위치·거리가 확정된 호재만 단지에 연결하고, 미확정 호재는 점수 가중치 0으로 표시만 한다.
13. **실거래 원본 우선**: 국토부 실거래가 Open API(공공데이터포털 키는 환경변수)를 1순위로, 전용면적·층·거래 취소 여부를 필드로 보관; 재가공 사이트는 폴백이며 "재가공" 라벨.

### 2-11 완료 조건 (설계가 이걸 다 만족해야 끝)

- `[지역]`만 바꿔도 코드 수정 없이 실행된다(지역 파라미터는 설정 파일)
- 청약홈 목록 두 개를 전수 조회하고 주소로 지역을 걸러낸다(단지명 검색 아님)
- 모든 수치에 출처 URL과 확인일이 있고, 추정·비공식·재가공·확인 불가·사람 확인 라벨이 빈칸 없이 붙는다
- 포함/제외는 사업주체 명의로 판정기가 분류하고, 오피스텔·공공분양·임대·범위 밖은 자동 제외된다
- 접수 가능 판정은 공식 출처와 사람 확인만 근거로 하고 비공식은 "가능"이 될 수 없다; 동적 팝업은 headless로 렌더링해 스크린샷을 남긴다
- 공고문 PDF 원문을 보관하고 추출값은 판정기 extract→audit를 거친다
- 사다리 명제는 템플릿 그대로이고(입주 후 1년 + 기준일+3년·+5년), 컨텍스트는 증거 카드+벤치마크+제도 3개다
- 종합 점수의 각 요소는 식으로 계산되고 가중치와 산출식이 표·툴팁에 적히며, 가중치 ±10%p 민감도가 자동 계산된다
- 가격 갭은 미보정값과 연식 보정값(추정)을 함께 보여준다
- 상황별 decide는 후보 ≤6·요건 3개·escape hatch 포함이고, 요건은 프로그램이 수치로 사전 계산해 증거에 적으며, warning과 증거 불일치를 그대로 보고하고 confidence < 0.6은 동률로 표기한다
- verify 주장은 원자 단위로 자동 분할되고, 섹션별 verify 후 최종 verify에서 contradicted 0이며, review는 미해결로 기록된다
- 판정기 호출은 입력 해시로 캐시되고 같은 입력 재호출이 코드로 막히며, 로그가 일련번호로 빠짐없이 부록과 운영 화면에 실린다
- rerank는 후보군 변경 시 전체를 1회 재실행하고 이전 점수와의 차이를 보여준다
- 홈페이지 403·DNS 실패·동적 팝업이 에러가 아니라 "확인 불가(사유·날짜)" 데이터로 화면에 남는다
- 지역을 추가하면 같은 문서에 장을 붙이고 통합 rerank·종합 점수·decide가 재실행된다
- G1~G8 화면이 모두 있고, 화면의 모든 숫자가 클릭 시 출처 원문으로 이어진다
- §2-7의 차트 10종이 명세대로 그려지고 표로 전환되며 다크 테마에서 읽힌다
- 사람 확인 입력(전화·방문)이 날짜·내용과 함께 저장되고 접수 상태에 반영된다
- 일·주 스케줄이 돌고 변경이 없는 날에는 판정기 호출이 0이다
- 기준일 스냅샷 두 개를 diff할 수 있고 보고서를 마크다운·PDF·Doc·CSV로 내보낼 수 있다
- API 키·개인정보가 판정기 전송 로그에 없다
- 판정기 모킹으로 오프라인 테스트가 돌고, 인천·김포 회귀 데이터로 돌렸을 때 §3-1의 숫자가 재현된다

### 3-3 다음 단계

1. `[지역]`을 인천 3개 신도시로 두고 설계 문서를 받은 뒤, §3-1 숫자가 재현되는지를 테스트 케이스로 삼는다.

3. 세 번째 지역(예: 고양 창릉·대장, 부천 대장)을 설정 파일만 바꿔 돌려 보고, 코드를 고쳐야 했다면 그 부분을 파라미터로 옮긴다.

## 4. 회고 — 이번 프로젝트에서 부족했던 점과 개선안 (메타 프롬프트에 반영된 근거)

가장 큰 구멍은 세 개였다. ① **접수 가능 여부를 거의 확인하지 못했다** — 김포 8개 잔여 단지 중 공식 확인 1개, 종합 점수 4위 스위첸은 홈페이지 403 하나 때문에 다섯 상황 모두에서 확률 0이 됐다. ② **점수의 절반은 사람이 손으로 매긴 등급이었다** — 공급 3, 유동성 9 같은 값은 재현도 검증도 어렵다. ③ **판정기를 일회성 수작업으로 불렀다** — 132회 호출과 서브에이전트 전수조사에 이틀이 걸렸고, 다음 달에 같은 일을 다시 하려면 처음부터다.
